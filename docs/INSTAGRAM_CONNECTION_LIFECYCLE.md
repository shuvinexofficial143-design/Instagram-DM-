# Instagram connection lifecycle

Settings lists only linked accounts backed by server credentials. Each row has targeted Reconnect and Disconnect actions. The Settings danger-zone button calls the same unlink operation. Explicit Disconnect hides the account, clears its credentials and public profile documents atomically, releases its plan slot, resets the selected-workspace cookie, and clears the client account cache. A remaining connected account becomes current when needed.

Generic Connect/Add starts fresh Instagram authorization with no retained target. Reconnect signs the selected Instagram IDs and restores only that linked identity. The callback passes the signed start time to the service-only database registration operation. Unlink and registration share a transaction lock; authorization started before unlink is rejected even after a subsequent fresh connection.

Historical memberships are archived rather than assigned to another owner. A fresh verified OAuth can attach a fully disconnected Instagram identity to another login in a separate workspace. Existing chats, customer records, rules and paused automation state remain with their original owner. Connecting an identity that is still live under another login returns an explicit conflict. Archived accounts do not consume connected-account allowance, but restoring one must still pass the current allowance.

Both operations use SECURITY INVOKER and are executable only by service_role; the Edge handler authenticates the website session and verifies Meta profile ownership before registration.

Validation: connection/API/OAuth and rendered UI regressions; account-store and automation suites; TypeScript and production build. `tests/instagram-lifecycle.integration.sql` tests the actual database registration functions, scoped-ID normalization, allowance release, same-owner restore, different-owner isolation, stale OAuth rejection, idempotent unlink, rollback on injected cleanup failure, and RLS using synthetic fixtures in a rolled-back transaction.
